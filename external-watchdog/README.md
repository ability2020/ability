# External paper-monitor watchdog

This is an independent **backup trigger**, not a replacement for the existing GitHub schedule. It checks whether the workflow has run recently and only dispatches a paper-monitor run when the latest run is older than 35 minutes.

## Safety and behavior

- Existing GitHub cron remains `7,22,37,52 * * * *` UTC.
- Configure cron-job.org to call the Worker at minutes `10,25,40,55` every hour (UTC). These checks happen three minutes after the expected GitHub schedule slots.
- A healthy recent run means the Worker returns `skipped_recent_run` and does not dispatch anything.
- If no workflow run has started within 35 minutes, the Worker dispatches the existing `bitget-test.yml` workflow on `main`.
- Backup dispatches set `run_historical_research=false`, so they do not start the long 5m/1H/4H research matrix.
- The Worker never calls Bitget and never places exchange orders.
- The Worker uses a GitHub fine-grained token with **Actions: write** permission, restricted to this repository. No token is stored in this repository.

The 35-minute threshold is deliberately conservative: one or two missed native schedule slots are given time for the next native trigger to recover. The watchdog intervenes only after three consecutive native schedule opportunities appear to have been missed, reducing the chance of creating a duplicate paper cycle just before the next scheduled slot. The watchdog is best-effort and does not guarantee uninterrupted GitHub Actions availability.

## 1. Create a fine-grained GitHub token

1. In GitHub, open **Settings → Developer settings → Personal access tokens → Fine-grained tokens**.
2. Create a token restricted to **Only select repositories → ability2020/ability**.
3. Set **Repository permissions → Actions → Read and write**. Do not grant Contents, Administration, or other permissions.
4. Give it an expiry date and create it.
5. Copy it once. Do not paste it into a chat, issue, commit, or repository file.

GitHub requires Actions: write for the workflow-dispatch API.

## 2. Deploy the Cloudflare Worker

1. Sign in to Cloudflare and open **Workers & Pages**.
2. Create a Worker named `ability-paper-watchdog`.
3. Replace its starter code with the contents of `worker.js` from this folder and deploy.
4. Open the Worker settings and add these two **secrets** (not plain-text variables):
   - `GITHUB_TOKEN`: the fine-grained token created above.
   - `WATCHDOG_SECRET`: a new long random secret generated by you (at least 32 random characters).
5. Save and redeploy if Cloudflare requests it.
6. Copy the Worker URL, for example `https://ability-paper-watchdog.<your-subdomain>.workers.dev`.

Keep both secrets private. The GitHub token must only exist as a Worker secret.

## 3. Configure cron-job.org

Create one job with:

- **URL:** your deployed Worker URL
- **Request method:** GET
- **Schedule timezone:** UTC
- **Hours:** every hour
- **Minutes:** 10, 25, 40, 55
- **Days/months/weekdays:** every day/month/weekday
- **Custom request header:** `Authorization: Bearer <the same WATCHDOG_SECRET>`
- **Notifications:** enable failure notifications if desired

This is 4 requests per hour (96 per day), within cron-job.org's documented default 100-request daily limit. Do not use cron-job.org's account API key as the Worker authorization secret.

## 4. Test safely

1. First open the Worker URL without the Authorization header. It must return HTTP 401.
2. Run the existing GitHub workflow manually from **Actions → Bitget Demo Bot Test → Run workflow**, leaving `run_historical_research` enabled only if you intentionally want the long research matrix.
3. Run the cron-job.org job once with the correct Authorization header. Since a recent workflow run exists, the Worker should return `skipped_recent_run` and must not create another run.
4. Check the cron-job.org execution history for HTTP 200 and the JSON response.
5. Only after this test succeeds should the recurring schedule be enabled.

## Troubleshooting

- HTTP 401: Worker Authorization header does not match `WATCHDOG_SECRET`.
- HTTP 500 mentioning a missing secret: configure `GITHUB_TOKEN` or `WATCHDOG_SECRET` as Worker secrets.
- HTTP 502 while inspecting runs: GitHub API could not be read; check the Worker logs and retry.
- HTTP 502 dispatch rejected: verify the token has Actions: write permission and access to `ability2020/ability`.
- `skipped_recent_run`: expected when a recent GitHub run exists.
- `backup_dispatched`: a backup workflow was requested. Confirm it appears in GitHub Actions.

Do not share either secret in screenshots or chat.
